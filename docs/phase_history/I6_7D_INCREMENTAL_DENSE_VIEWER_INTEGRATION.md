## What is implemented

- Dependency-light I6.7D projector: provisional I6.7A geometry samples -> bounded, contiguous **float32** Z-up vertex and RGBA arrays. 4,096-point maximum, 114,688 final staging bytes (positions + colors). Vectorized projection; the actual dense result remains on its existing provider path, never in the viewer staging buffers.
- Reuses the existing VisPy SceneCanvas/OpenGL rendering path with a **separate** marker visual for provisional dense geometry, completely separate from canonical persistent Dense RGB Points. No new GPU device/model inference or hard-coded RTX requirement. GL work is restricted to the Qt canvas-owning thread.
- Status-only revisions update the visible stage but do **not** rebuild point/color arrays, call VisPy marker `set_data`, or request a canvas redraw. Only new geometry revisions replace the one GPU preview; no historical point-cloud accumulation. No camera refit after the first new preview.
- A page-side explicitly run-bound `ProgressiveDenseSnapshotBuffer`, single pending snapshot, 33 ms single-shot frame pacing, coalescing and strict run/source/frame/revision checks. A queued Qt signal allows already-decoded snapshots from a producer thread to be submitted on the GUI thread without allowing GL calls off-thread; no new mandatory decoding or GL worker thread is introduced for the bounded 4,096-point preview.
- New-run, cancellation and failure lifecycle clears only provisional previews and pending timers; a completed-but-not-yet-admitted dense preview remains visibly **provisional** until a new run or an independently admitted persistent scene supersedes it. Canonical geometry and the I6.6 sparse preview remain independent.
- Optional isolated UI replay uses the frozen, SHA-checked I6.7B JSONL: one geometry snapshot in the real evidence is expected. It does not execute PatchMatch, Stereo Fusion or promote final dense geometry.

## Performance and GPU correctness

The GPU handles VisPy point rendering, not the scientific dense reconstruction. The external PyCOLMAP CUDA PatchMatch worker continues on its existing isolated path. Upload requests are bounded by *actual new geometry revisions*, not by status-message count. Processing 4,096 points with an extra mandatory Python compute thread would add synchronization overhead; the code instead bulk-converts once to 2 compact arrays, supports queued Qt-thread delivery of already-decoded snapshots, and leaves decoding threads / device selection to the qualified producer side. The page counters count **visual submissions**, not measured OpenGL driver transfer time, GPU utilization, or end-to-end FPS. Page telemetry also records latest/peak bounded CPU projection + VisPy submission latency, deliberately excluding the one-time fit and asynchronous GPU rasterization/present. No promise of 30 FPS is implied by the 33 ms frame scheduler; that is only the maximum scheduling frequency. Do not infer 2060/4090/5090 performance from a CPU-only microbenchmark.
